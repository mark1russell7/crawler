Do not edit this file. Change the item file, then start `pnpm roadmap`. Each item has an id, a status, an area, the items it waits for, dates and links.

### `study-recompute`: The robots.txt study: count the rules again with each version of the parser

The 4 pages of the robots.txt study show counts from the robots.txt parser of polite-crawler. The freshness gate of the site template asks each page to name the version of the parser that computed its numbers. From 2026-11-30 a page fails when that version is more than one minor version behind the package. The counts of 2 November 2026 came from 0.2.4, and the package is 0.7.6. The fix keeps the robots.txt files of the newest run in the repository (about 2.4 MB, gzip). At each commit, CI counts the rules again with the parser of the workspace, and the stamp names that version. Then a new version needs no new fetch: the 33-day limit holds the age of the fetch only. When a new parser changes a verdict, CI lists each changed site. The page copy then takes the new counts and says how many sites changed. The files of each run on Zenodo stay as they are. Due before 2026-11-30.

### `api-fresh-until`: freshUntil in polite-crawler/api: when a kept answer is stale

An API client that keeps the answers of poll and send must know when to ask again. The crawler already calculates the end of the freshness of each capture (RFC 9111: max-age, Expires minus Date, then 10 percent of the age of Last-Modified, with a maximum). #169 moves that calculation to its own module and exports it from polite-crawler/api as the beta function freshUntil, in milliseconds since the epoch. The field fresh_until of a capture does not change. The alerts sources asked for it and wrote the PR. The review passed, main (0.7.3) is merged into the branch, and CI runs. It ships in 0.7.4 with the watch-list fix of #170.

### `quota-followups`: Quotas: the follow-ups of the reviews (a list of gates, the reset forms, the longest block, onError)

Five follow-ups from the reviews of the quotas, in 0.7.0 (#162). 1. Two quotas on one call: withQuota takes a list of gates and counts the call in each gate or in none. When one gate refuses, the other gates give back their units, because the call did not start. A give-back changes nothing when a reading of the provider came after the take, so the count never goes below the count of the provider. 2. The doc of resetAfter says: a value that the gate can read. 3. A reset header in seconds until the reset (RateLimit-Reset of the IETF draft) is read as such, and a reset in milliseconds since the epoch too, not as a time in 1970 or in the year 59000. 4. The README warns that a reset header with no count stops the key, even on a 200. 5. From the review of #162: a block of the provider ends at the latest one window after the reading (option maxBlockMs), also a block that a store keeps from an earlier version; an error that onError throws is lost, so the caller keeps the refusal and each gate still gives back. Seven mutants of these fixes fail the tests. Released in polite-crawler 0.7.0 on 2026-11-15 (#162, merged dff2fe8).

### `quota-service`: Quotas: move the window counting to @mark1russell7/service

The window counting of quotaGate (rolling buckets and calendar days and months in a zone) is a limiter, and the map of homes puts limiters in @mark1russell7/service. Systems built it in #527 (SYS-115, merged 2616fe7) as @mark1russell7/service/limiter: quota specs as quantities, a pure quotaStep, keyedQuota on a wall clock, and takeQuotas, all or none, with the give-back and readAt rules of polite-crawler 0.6.4. Its QuotaRecord and QuotaStore have the same shape as those of polite-crawler, so the files of SqliteHostStateStore do not change. The plan: quotaGate becomes an adapter over keyedQuota, a list in withQuota goes to takeQuotas, and the two record types become those of service. polite-crawler keeps the header reading (readQuotaHeaders), QuotaError and withQuota, and its QuotaStore with changeQuota (an adapter gives it the change method of service, so a store of your own does not break). A check of service 0.8.17 on 2026-11-15 found two gaps: no bound on a provider block (polite-crawler 0.7.0 caps it at maxBlockMs, by default one window), and a part of takeQuotas had to be a full KeyedQuota, so a gate of your own could not be one. Systems #535 added both: maxBlock in QuotaSpec and a narrow part type. The crawler side is written on a branch: quotaGate maps a quota to a spec of the limiter and keeps its store through an adapter, a list of gates takes through takeQuotas, and the crawler no longer needs @mark1russell7/algebra. Its 102 quota, host-state and API tests pass on a build of service with #535. The release train published service 0.8.18 seven seconds before #535 merged with the same number, so #535 ships as 0.8.19 (systems #538). Service 0.8.19 is on npm. The move then failed the browser size budget of polite-crawler/api: 16.6 KB gzip against 8.15 KB. Systems #543 made the limiter leaner (service 0.8.20, quantity 0.4.1: a time-only unit table, one file per module, rational imported by name): its three imports go from 11.2 KB to 7.7 KB gzip. The rest is the quota logic and the exact unit conversion, which stay (the quantity law). Only quotaGate and withQuota bundle the limiter. On service 0.8.20 the whole api entry is 13.4 KB gzip (7.9 KB in 0.7.4), the entry without those two functions is 4.9 KB, and fetchTransport alone is 0.8 KB. The decision: the budget of the whole entry is 16102 B (the size and 20 percent more), and a second budget in the smoke check holds the entry without the two functions at 5898 B. A new export of api counts in that part by default. CI agreed with the local sizes (13418 B and 4915 B). A new release check of the shared CI (pinned on 2026-11-15) fails a pull request that changes shipped files at a version on npm, so #171 carries its version: 0.7.5, a PATCH (no change to the public API). It merged on 2026-11-15 (468e5cc), and polite-crawler and polite-crawler-mcp 0.7.5 are on npm with provenance.

### `report-chunks`: API report: no chunk paths (html.chunk.d.mts)

The API report named build/html.chunk.d.mts 24 times. A chunk name is not a stable API: a change of the bundler renames the chunk, and the report then shows a break that is not real. The cause: html.ts and text.ts were needed by the same entries, so the bundler put them in one chunk. The fix makes text.ts (the body decoder, with no imports) an entry point of its own, polite-crawler/text, as urls became one in 0.5.1. The first try, a merge of text.ts into html.ts, broke the JavaScript budget of the site (146,597 bytes over 40,000). Two new tests: the report names only entry points, and the counts table of the API review matches the reports. In #162 with api-guards and quota-followups. The version is 0.7.0 (MINOR before 1.0: read of withQuota gets the gate, and that breaks a program that calls read itself). ### `api-quota`: API quotas: count each key over its day, month or window, and stop before the provider

For the alerts project: free API keys have a documented quota (as read on 2026-11-14: Pushover 10,000 messages a month for each user account, reset at 00:00 Central Time on the 1st; NASA FIRMS 5,000 transactions in 10 minutes; OpenSky 400 to 8,000 credits a day for each endpoint group; TomTom 200,000 tiles and 20,000 other map requests a month). polite-crawler/api paced each host and reacted to a 429, but it counted no quota, so a program found the limit only when the provider refused it. quotaGate counts each key over a calendar day or month in a time zone, or a rolling window, with a cost for each call and a reserve. withQuota puts the gate on any async function (a fetch, a transport, a client), so a call over the quota is refused with its reset time and no request goes out. The headers of the provider make the count larger, never smaller. The counts stay after a restart in the SQLite host state store (schema 2 through @mark1russell7/sqlite). After the review: each quota name and key has its own record, so a gate of a minute and a gate of a day on one key count apart. The civil time comes from @mark1russell7/algebra/clock: a window that starts in a clock gap starts at the end of the gap, and in an overlap at the first time. An error of the store after a call goes to onError, so a retry does not send the call twice. Released as polite-crawler 0.6.3 on 2026-11-15, with npm provenance. The four follow-ups of the review are the item quota-followups (0.6.4), and the move of the window counting to @mark1russell7/service is the item quota-service.

### `html-size`: The html entry grew 25 % with linkedom 0.18.15

linkedom 0.18.15 (2026-11-01) bundles the CSS parser cssomnom in place of @acemir/cssom. The gzip size of polite-crawler/html went from 128362 to 160188 bytes (+25 %), over the 138000 budget. #80 raised the budget to 192000 to unblock CI. Measured on 2026-11-15 (esbuild, browser, minified, as the smoke test): 160,172 bytes gzip, 499,612 raw, and cssomnom is 199,261 raw bytes (40 %). linkedom uses it in one place, the lazy getter HTMLStyleElement.sheet. extractPage and Readability never read it, but a bundler cannot drop a static import of a class that it keeps. A browser build that uses the DOMParser of the browser does not work: the page reader of the site runs extractPage in a Web Worker, and a worker has no DOMParser, so linkedom must ship. A pin to linkedom 0.18.14 is debt with no end. The decision: accept the size. The budget of 192,000 is already the size with 0.18.15 and 20 percent more, as for each other entry, and smoke.ts states the reason. The end of the debt is a new check in the smoke test: a budget more than 40 percent over its size fails. So when a linkedom version drops cssomnom (html near 128 KB), the PR that brings it must lower the budget, and each entry that shrinks 15 percent keeps its gain. A request to linkedom for a lazy CSS parser is outside this project, so it is not made.

### `daemon-lock`: Daemon: a lock file for the single-daemon rule

Two `polite-crawler daemon` starts at the same moment on one store both passed the single-daemon check, so both ran and the second replaced the MCP token file. The fix: the daemon holds the lock file <store>/daemon/lock until it stops, from acquireInstanceLock of @mark1russell7/service (an exclusive create, and the next start removes a stale lock of a stopped process). A failed start and the stop give the lock back. Two new tests: two starts at one moment give one daemon, and a stale lock goes. Found by an audit; rare. In PR #167 as 0.7.2 (PATCH). #167 merged (9559aae) on 2026-11-15. Its release run was still in the queue when #168 (0.7.3) merged, so the fix reaches npm in 0.7.2 or, if the newer run replaces it, in 0.7.3.
